# imgc · MVP 功能设计方案

> 本文只是**设计方案文档**，不含任何实现代码。目标是把 MVP 要做成什么样、怎么用、参数怎么定、边界怎么处理写清楚，评审通过后再动手写代码。
>
> 项目目标：把"给 DSH 传图"这件事从"手工调图 + 反复被拒"变成"按一下就好"。

---

## 0. 一句话概括

做一个叫 **imgc** 的本地小工具，由一个**压缩引擎**和三个**入口**（全局热键召出的图形界面、命令行、拖拽）组成：

```
截个图  →  按 Ctrl+Alt+C  →  点一下"压缩最新截图"  →  回到 DSH 输入框 Ctrl+V
```

同时支持批量选文件、拖文件进来、命令行处理，压缩参数可保存成预设，结果既能回写剪贴板也能存到指定目录。

---

## 1. 目标与非目标

### 1.1 MVP 必须达成的目标

| 编号 | 目标 | 可验证的标准 |
|---|---|---|
| G1 | 一次压缩就能通过 DSH 的图片准入 | 压缩结果同时满足"单边 ≤2000px、体积达标、格式在白名单" |
| G2 | 从截图到粘贴进 DSH ≤ 3 步 | 截图 → 热键+点击 → Ctrl+V |
| G3 | 有图形界面，能快速召唤 | 全局热键 `Ctrl+Alt+C` 唤出/隐藏 |
| G4 | 默认动作就是"压缩最新截图" | 打开窗口后主按钮已聚焦，回车即执行 |
| G5 | 支持批量：多选文件 / 拖入 | 一次处理多个文件并汇总结果 |
| G6 | 有命令行 | 终端一条命令完成同样的压缩 |
| G7 | 参数可配置、可预设 | 至少 5 套预设 + 单次覆盖参数，且能存进配置文件 |
| G8 | 两种输出方式，界面和命令行都能用 | 回写剪贴板 / 保存到指定目录 |

### 1.2 明确不做（MVP 之外）

- ❌ 浏览器插件 / DSH 客户端插件（列为 P2，理由见 §16）
- ❌ 监视文件夹、自动监视剪贴板（P2）
- ❌ 系统托盘图标、悬浮球（P1，见 §15；MVP 用"置顶小窗 + 全局热键"替代）
- ❌ 视频、GIF 动图压缩
- ❌ 图片编辑（裁剪、涂鸦、打码）
- ❌ 云端上传、图床
- ❌ 修改 DSH 自身的任何配置或代码

## 2. 设计依据：DSH 的图片限制（决定所有默认参数）

以下数值来自 DSH 0.1.0-rc.7 的实际源码，不是估算。

| 关卡 | 限制项 | 源码默认值 | 你这台机器当前生效值 | 超限时 DSH 的提示 |
|---|---|---|---|---|
| ① 浏览器前端预检 | 单张体积 | 3.5 MiB | **20 MiB**（注1） | 单张图片不能超过 {size} |
| ① | 张数 | 20 张 / 条消息 | 20 | 最多 {count} 张，每张 {size} |
| ① | 单条消息图片总量 | 100 MiB | 100 MiB | 单条消息图片总量超限 |
| ① | 允许格式 | png / jpeg / webp / gif | 同 | 直接拒绝（不发送） |
| ② 宿主附件服务 | **单边最大像素** | **2000 px** | **2000 px（无法靠补丁放宽）** | 图片宽高不能超过 2000px，请缩小后重试 |
| ② | 总像素（宽×高） | 4000 万 | 1 亿（注1） | 图片分辨率过大，请压缩后重试 |
| ② | 单张体积 | 3.5 MiB | 20 MiB（注1） | IMAGE_TOO_LARGE |
| ② | 声明格式必须与真实字节一致 | 强校验 | 同 | 改文件后缀无效 |
| ③ 模型请求层 | 一次请求累计图片体积（base64 编码后） | **20 MiB** | 20 MiB | **不报错**：最老的图片被静默替换成一行文字 |
| ③ | 模型须支持图片输入 | inputModalities 含 image | — | does not accept image input |

**注1**：你安装的 `dsh-vision-router` 插件自带的补丁把附件限制放宽到了 20 MiB / 1 亿像素（该补丁行与插件行相互独立，即使你在 `cordis.patch.yml` 里 `disabled: true` 掉了插件行，放宽依然有效）。但 **2000px 单边限制没有被放宽**。

### 2.1 从限制推导出的三条铁律

1. **长边必须 ≤ 2000px** —— 这是无法通过改配置绕过的硬墙（源码注释说明：部署的模型路由在图片较多时会拒绝单边超过 2000px 的请求）。因此 imgc 的默认长边就定 2000，并且**缩放是默认动作，不是可选项**。
2. **单张目标体积定 800 KB** —— 原因在关卡③：一次请求所有图片的 base64 累计上限是 20 MiB，而 base64 会让体积膨胀约 1/3，所以真实图片总量预算 ≈ 15 MiB，而且这是**整段对话历史累计**。按每张 800 KB 算，一个会话里能稳稳留住约 19 张图，老图不会被悄悄"挤掉"。
3. **只输出 png / jpeg / webp 三种** —— GIF 虽然允许，但作为输出格式没有压缩优势；输入的 BMP/HEIC/AVIF 一律转换进这三种。

> 结论：即使将来卸掉 vision-router、单张限制掉回 3.5 MiB，imgc 的默认参数（2000px / 800KB）依然完全够用——这就是把默认值定得比当前上限保守很多的原因。

## 3. 总体架构

```
                    ┌─────────────────────────────────────────────┐
                    │           引擎 imgc（纯逻辑，无界面）          │
                    │  读图 → 缩放 → 编码 → 达标校验 → 输出         │
                    │  唯一实现压缩算法的地方，被下面三者共用          │
                    └─────────────────────────────────────────────┘
                          ▲                ▲                 ▲
              ┌───────────┘                │                 └───────────┐
              │                            │                             │
    ┌──────────────────┐      ┌─────────────────────┐      ┌──────────────────┐
    │ 入口A：图形界面   │      │ 入口B：命令行        │      │ 入口C：拖拽/快捷方式│
    │ tkinter 小窗      │      │ imgc a.png --target │      │ 文件拖到 imgc.cmd │
    │ 全局热键召唤      │      │ 可脚本化、可 --json  │      │ 或 .lnk 快捷键    │
    └──────────────────┘      └─────────────────────┘      └──────────────────┘
              │                            │                             │
              └──────────────┬─────────────┴──────────────┬──────────────┘
                             ▼                            ▼
                   ┌──────────────────┐        ┌──────────────────────┐
                   │ 输出1：回写剪贴板 │        │ 输出2：保存到目录      │
                   │ (PNG + 位图双格式)│        │ 文件名带尺寸与体积信息  │
                   └──────────────────┘        └──────────────────────┘
```

**核心设计原则**：压缩逻辑**只有一份**，放在引擎里；界面、命令行、拖拽只是三种"调用方式"。这样避免"界面压得出来、命令行压不出来"这类不一致，也让 Agent（也就是我）能直接用命令行调用它。

## 4. 技术选型（已在本机实测通过）

| 部件 | 选型 | 实测结论 | 选择理由 |
|---|---|---|---|
| 语言 | Python 3.14.0 | ✅ 已装 | 免安装、生态成熟 |
| 图像处理 | Pillow 12.0.0 | ✅ jpg / zlib / webp 全部可用 | 缩放+编码一体，够用且快 |
| 界面 | **tkinter 8.6**（Python 自带） | ✅ 已装 | 零额外依赖；启动快（比 Qt 轻得多）；做这种小工具窗足够 |
| 剪贴板读取 | `PIL.ImageGrab.grabclipboard()` | ✅ 存在 | 一行代码同时处理"位图"和"复制的文件"两种剪贴板内容 |
| 剪贴板写入 | `ctypes` 调 Windows API | 标准库 | ImageGrab 只能读不能写，写需自己实现（§9.1） |
| 全局热键 | `ctypes` 调 `RegisterHotKey` | 标准库 | 不装第三方软件就能实现全局热键 |
| 隐藏控制台启动 | `pythonw.exe` | ✅ 存在于 Python 安装目录 | 用界面时不留黑窗口 |

**为什么不用 Electron / Qt / 网页前端**：这些方案启动慢、体积大（几十到几百 MB），而本工具的价值就在于"快"——按完热键要能**瞬间**弹窗。tkinter 冷启动通常在 0.3 秒以内。

**为什么不用 Node + sharp**：sharp 编码更快、画质更好，但需要单独安装一份依赖；而截图这种尺寸（通常 2–8 百万像素）Pillow 完全够快。若将来处理超大图感觉慢，可作为 P1 替换引擎（架构上引擎是独立的，换掉不影响界面）。

## 5. 操作形态总览

### 5.1 三种唤出方式

| 方式 | 操作 | 说明 |
|---|---|---|
| **全局热键**（主） | 按 `Ctrl+Alt+C` | 在任意程序里都有效；窗口未开则弹出，已开则隐藏到后台。热键可在配置里改 |
| 快捷方式 | 双击桌面/开始菜单的 `imgc.lnk` | 热键注册失败时（被别的软件占用）的备用方案；可另行给它设 Windows 原生快捷键 |
| 命令行 | 终端输入 `imgc ...` | 也可 `imgc --gui` 显式打开界面 |

**热键的两种模式**（配置项 `hotkeyMode`）：

- `summon`（默认）：唤出窗口并聚焦到"压缩最新截图"按钮 —— **可见、可控**，适合刚开始用。
- `instant`：**不弹窗**，直接后台压缩剪贴板里的图 → 回写剪贴板 → 右下角冒一个 2 秒的小提示（"已压缩 3.2MB → 412KB"）。这是给熟练后追求极致速度的档位。

### 5.2 三种操作方式

| 方式 | 入口 | 交互 |
|---|---|---|
| **A. 压缩最新截图**（默认动作） | 界面主按钮 / 回车 / （可选）纯热键 | 读剪贴板 → 压缩 → 按输出设置处理。**这是 90% 的场景** |
| **B. 批量选择** | 界面按钮"选择文件…" | 弹出多选文件对话框，记住上次目录；支持混选不同类型 |
| **C. 拖入** | 文件拖到窗口上 / 拖到 `imgc.cmd` 上 | 分两级实现，见下 |

关于**拖入的分级实现**（tkinter 原生不支持窗口内拖放，这点必须提前说明）：

- **P0（零成本，MVP 内）**：把文件直接拖到 `imgc.cmd` / `imgc.lnk` 上 —— 这是 Windows 自带的"拖到程序上打开"机制，不需要写一行拖放代码，立刻可用。
- **M2 增强（窗口内拖放）**：两条路线二选一 ——
  - 路线一（推荐）：装 `tkinterdnd2` 这个小库，几行代码搞定；
  - 路线二（坚持零依赖）：用 `ctypes` 子类化窗口过程，接收 `WM_DROPFILES` 消息 —— 可行但需要约 60–80 行 Windows API 代码，且有 32/64 位句柄的坑。
  - **建议先走路线一**，理由：一个纯 Python 小库的安装成本，远低于自己维护窗口子类化代码的长期风险。

### 5.3 输出方式（界面与命令行都能用，可同时开启）

| 输出 | 默认 | 说明 |
|---|---|---|
| **回写剪贴板** | ✅ 开 | 压缩结果直接放回剪贴板，切到 DSH 按 Ctrl+V 就完成 |
| **保存到目录** | ✅ 开 | 目录可在界面选择/命令行指定；文件名自动带尺寸和体积 |
| 附带复制文件路径 | ⬜ 关 | 需要引用路径时用（比如你想说"看下这个文件"） |
| 完成后打开目录并选中 | ⬜ 关 | 需要去文件夹里拿图时开 |

## 6. 界面设计

### 6.1 窗口形态

- 尺寸约 **560 × 480**，**置顶**（always on top，但可切换），**可拖动**，无边框或极简边框。
- 位置记忆：记住上次拖动到的位置，下次原地弹出（避免每次都去屏幕中间找）。
- **单实例**：重复启动时不自开第二个窗口，而是把已有的窗口唤到前台（实现方式见 §11.3）。

### 6.3 控件行为表

| 控件 | 行为 |
|---|---|
| 拖放区 | 拖入 1 个文件 = 单张处理；拖入多个 = 批量处理；拖到窗口任意位置都算（不用瞄准某个框） |
| 预设下拉 | 切换预设会**联动**刷新长边/目标体积/格式/质量；手动改任一参数则自动切到"自定义" |
| 长边输入框 | 超过 2000 时输入框**变黄并提示**："DSH 单边硬限制是 2000px，超过会被拒" |
| 目标体积 | 填 0 表示不限制体积（只按长边压缩） |
| 质量滑块 | 选 PNG 格式时**禁用**（PNG 无损，没有质量概念） |
| 「记住本次设置」 | 勾选后，本次参数写进配置文件，下次启动沿用 |
| 「压缩最新截图」 | 主按钮，窗口打开即聚焦；**回车**等同点击；热键模式下支持连按两次热键退化为触发（P1） |
| 「选择文件…」 | 多选对话框，默认打开上次使用的目录 |
| 结果区按钮 | 「再次复制」= 把上次结果重新写回剪贴板（防止被其他复制操作覆盖） |

### 6.4 界面状态机

| 状态 | 表现 |
|---|---|
| 空闲 | 主按钮可用，结果区显示上次结果（或"还没有处理过图片"） |
| 处理中 | 按钮变灰 + 进度显示"正在处理 3/12…"，窗口不冻结（耗时工作放后台线程） |
| 成功 | 结果区显示前后对比 + ✅；若开了保存，显示保存路径 |
| 部分失败 | 批量时逐个显示成功/失败，失败项用 ❌ 标红并给出原因 |
| 失败 | 顶部红色提示条，说明失败原因和对策（如"剪贴板里没有图片，请先截图或复制一张图"） |

## 7. 压缩参数模型

### 7.1 预设（日常只用这一层）

| 预设 | 长边 | 目标体积 | 格式策略 | 适用场景 |
|---|---|---|---|---|
| **`dsh`**（默认） | 2000 | ≤ 800 KB | 有透明→PNG，否则→WebP q82 | 通用截图，一个会话能留住约 19 张 |
| `dsh-big` | 2000 | ≤ 3 MB | WebP/JPEG q88 | 要看清细节的设计稿、报错截图 |
| `text` | 2000 | ≤ 500 KB | WebP q90，必要时 PNG-8 | **文字/代码截图**：比 JPEG 清晰得多且更小 |
| `tiny` | 1280 | ≤ 200 KB | WebP q75 | 一次要传很多张、只看个大概 |
| `photo` | 2000 | ≤ 1 MB | JPEG q85 | 照片 |
| `long` | 单边 2000 | — | **纵向切片**，每片高 ≤1800，重叠 60px | 长截图、整个聊天记录 |

> 关于 `long`：长截图（比如 1080×8000）单边远超 2000px，直接缩到 2000 会糊到看不清字。**切片**是唯一既能通过限制又能看清内容的办法。DSH 允许一条消息带 20 张图，所以切 5–8 片完全没问题。重叠 60px 是为了避免正好把一行文字切成两半。

### 7.2 单次覆盖参数

| 参数 | 含义 |
|---|---|
| `--long-side N` | 长边像素上限（默认 2000） |
| `--max-side N` | 任意单边上限（长截图时比 long-side 更严格） |
| `--target 800kb` | 目标体积，支持 `kb` / `mb` 单位，`0` = 不限 |
| `--format auto\|png\|jpeg\|webp` | 输出格式，`auto` 按预设策略 |
| `--quality 82` | 编码质量 40–95 |
| `--split 1800` | 启用纵向切片，指定每片高度上限 |
| `--overlap 60` | 切片重叠像素 |
| `--bg white\|black\|#f5f5f5` | 透明背景转不透明时的底色（JPEG 不支持透明） |
| `--gray` | 灰度化（文字截图可再省约 30%） |
| `--if-needed` | 只有超标才压缩（**默认行为**，避免无意义重编码掉画质） |
| `--check` | 只体检不压缩，报告是否超标、超在哪一项 |
| `--no-clip` / `--no-save` | 关闭某一种输出 |
| `--out DIR` | 输出目录 |
| `--json` | 输出机器可读结果（方便脚本和 Agent 调用） |

### 7.3 自动达标算法（核心逻辑）

参数只要给"目标"，具体怎么压不需要用户操心：

```
1. 读图，记录原始 尺寸 / 体积 / 格式
2. 若开启了 --if-needed 且原图已达标 → 直接放行，不重编码（保住画质）
3. 缩放：长边 > 上限 → 按比例缩到上限（用 LANCZOS 高质量重采样）
4. 编码并逼近目标体积：
   · WebP / JPEG：先按 quality 编码；若超目标，质量每次降 6 再试；
     降到 40 还超 → 长边再缩 15% 重来；最多 3 轮
   · PNG：先开 optimize 编码；仍超 → 转调色板（256 色 → 128 → 64）
     ※ 截图颜色数通常很少，转调色板常常能省 70% 以上且看不出差别
5. 终检：单边 ≤2000、总像素 ≤1 亿、体积 ≤目标，全部通过才输出
6. 输出 + 生成结果摘要
```

**通俗解释"逼近"**：就像调水龙头——先拧到一个位置，出水太多就往回拧一点，太少就再拧开一点，直到刚刚好。用户只需要说"我要 800KB 以内"，工具自己去试质量参数，不用你手动试十几次。

## 8. 命令行设计

### 8.1 命令

```bash
imgc                            # 压缩剪贴板里的最新截图 → 回写剪贴板 + 存到默认目录
imgc a.png                      # 压缩指定文件

imgc *.png                      # 通配符批处理

imgc -p text --target 300kb a.png
imgc --no-clip --out D:\pics a.png
imgc --split 1800 long.png      # 长截图切片
imgc --json a.png               # 输出结构化结果
imgc --gui                      # 显式打开图形界面
imgc --presets                  # 列出所有预设及其参数
```

### 8.2 默认行为（不带参数时）

无参数运行 = **压缩剪贴板里最新的图片**（等价于界面上的主按钮），完成后打印一行摘要并把结果写回剪贴板。这让"命令行"和"界面"的默认语义完全一致，不会有两套心智模型。

### 8.3 退出码

| 码 | 含义 |
|---|---|
| 0 | 全部成功 |
| 1 | 参数错误 / 输入文件不存在 / 剪贴板里没有图片 |
| 2 | 全部失败 |
| 3 | 部分失败（批量场景，逐项结果在输出里） |

### 8.4 `--json` 输出示例

```json

  "items": [
```

## 9. 输出设计

### 9.1 回写剪贴板：为什么要写两种格式

剪贴板不是"一个东西"，而是一张**多格式货架**：同一个内容可以同时以多种格式摆上去，取用方挑自己认识的。所以压缩结果要同时以两种格式放上去：

- **PNG 格式**（注册的自定义格式名 `PNG`）：浏览器（Chrome/Edge）优先读它，能拿到**精确的压缩后字节**——我们用 WebP/JPEG 压出来的成果就靠这个保住。
- **位图格式**（`CF_DIB`）：画图、Word、微信等传统桌面程序读它。

只写一种会出现"浏览器能粘、画图不能粘"（或反过来）的怪毛病。写入用 `ctypes` 调 `OpenClipboard` / `SetClipboardData` 等 Windows API 实现，约 150 行。

读取则简单得多：直接用 `PIL.ImageGrab.grabclipboard()`，它能同时处理：
- 剪贴板里是**位图**（Win+Shift+S 截图后的情况）→ 返回 PIL 图片对象；
- 剪贴板里是**复制的文件**（在资源管理器里 Ctrl+C 一个图片文件）→ 返回文件路径列表。

### 9.2 保存到目录

命名规则（信息一目了然，方便事后追溯）：

```
<原名或来源>-<预设>-<宽>x<高>-<体积>.<扩展名>
例：screenshot-dsh-2000x1125-412KB.webp
    长截图切片：long-long-01of06-1080x1800-380KB.webp
    剪贴板来源：clip-20260917-143052-dsh-2000x1125-412KB.webp
```

- 同名文件自动加 `-2`、`-3` 序号，**绝不覆盖**已有文件。
- 默认输出目录：`%USERPROFILE%\Pictures\imgc\`（首次运行时自动创建）；界面上可改，命令行用 `--out` 指定。

### 9.3 结果摘要（界面与命令行都要有）

固定输出这五项，让人一眼判断"能不能用"：

```
原图  3840×2160  PNG  3.21 MB
新图  2000×1125  WebP 412 KB
压缩率 87%    ✅ 符合 DSH 限制（长边2000 ≤2000 · 体积412KB ≤800KB · 格式WebP ✅）
```

### 11.1 引擎接口（先定契约，再写实现）

```python
# engine.py
def compress_one(src, params) -> Result
    # src: 文件路径 | PIL.Image | 剪贴板内容
    # params: 归一化后的参数对象（长边/目标体积/格式/质量/切片…）
    # Result: 原图信息、新图信息、字节数据、是否达标、失败原因

def inspect(src) -> Report       # 只体检（--check 用）
def split_long(img, height, overlap) -> list[Image]   # 长截图切片
```

界面的"压缩最新截图"、命令行的 `imgc a.png`、拖拽入口，最终都调用 **同一个** `compress_one`。

### 11.2 线程模型

- 界面主线程只负责画界面；
- 压缩在**后台线程**里跑，通过队列把进度和结果回传主线程更新界面；
- 理由：12 张图批量压缩要几秒，若在主线程做，窗口会"假死"（转圈、点不动），体验极差。

### 11.3 单实例机制

用 Windows 的"命名互斥体"（`CreateMutexW`）判断是否已有实例在跑：

- 已有实例：把本次请求（比如"处理这些文件"）记进一个临时文件，然后**自己退出**；主实例轮询到新请求就执行，并把窗口唤到前台。
- 好处：无论你从热键、命令行还是拖拽进来，永远只有一个界面，不会开出一堆窗口。

## 12. 关键流程时序

### 流程一：截图 → DSH（最常用，3 步）

```
用户  Win+Shift+S 框选          → 图片进入系统剪贴板
用户  按 Ctrl+Alt+C             → 热键线程收到 → 窗口弹出并聚焦主按钮
用户  回车                      → 后台线程：读剪贴板 → 缩放2000 → WebP逼近800KB
                                  → 写回剪贴板(PNG+位图) → 存到目录 → 结果区显示对比
用户  切到 DSH 输入框 Ctrl+V    → 附件出现（412KB / 2000×1125 / WebP）→ 回车发送
```

### 流程二：批量处理

```
拖入 8 个文件（或点"选择文件…"多选）
→ 逐个压缩，界面显示"正在处理 3/8…"
→ 汇总：7 成功 1 失败（失败项标红：某张是 AVIF，已自动转换为 WebP / 或某张文件损坏）
→ 全部结果存入输出目录；若只有 1 张，同时回写剪贴板
```

### 流程三：命令行

```
imgc --check shot.png        → 报告：3840×2160 3.21MB → ❌ 超限（单边3840>2000）
imgc -p text shot.png        → 输出 .../shot-text-2000x1125-268KB.webp
imgc --json shot.png         → 结构化结果（见 §8.4）
```

## 13. 边界与错误处理

| 情况 | 处理方式 |
|---|---|
| 剪贴板里没有图片 | 提示"剪贴板里没有图片，请先截图或复制一张图"，不报错崩溃 |
| 剪贴板里是复制的**文件** | 自动物化为临时文件后正常处理 |
| 输入是 BMP / HEIC / AVIF / TIFF | 自动转成 png/jpeg/webp；HEIC 需可选组件 `pillow-heif`，缺失时明确提示"需要装一个小组件才能读 HEIC" |
| 透明 PNG 要输出 JPEG | 按 `--bg`（默认白色）铺底，避免透明区域变成黑块 |
| 图片本来就没超标 | 默认**原样放行**（`--if-needed`），不重编码 |
| 长截图 1080×8000 | `long` 预设自动切片；若用户没选切片，提示"长边 8000 超限，建议用 long 预设切片" |
| 目标体积小到不可能达成（如 4K 无损要 ≤50KB） | 走到算法下限后明确告知"已压到极限 120KB，仍高于目标 50KB"，并给出建议（改格式/允许有损/放大目标），**绝不偷偷交一张糊图** |
| 输出文件已存在 | 自动加序号，不覆盖 |
| 目录无写权限 | 提示具体路径和原因，并自动回退到默认目录 |
| 配置文件损坏 | 备份为 `config.json.bak`，用内置默认值启动 |
| 热键被别的软件占用 | 注册失败时提示，并给出替代方案（改用 `.lnk` 快捷方式的 Windows 原生快捷键，或改配别的组合键） |
| 输出格式是 GIF | 拒绝并说明：GIF 作为输出没有压缩优势，建议 WebP |

## 15. 里程碑

| 阶段 | 内容 | 产出 |
|---|---|---|
| **M1** | 引擎 + 命令行 | `engine.py` / `cli.py` / `clipboard.py` / `config.py`；此时"命令行 + .lnk 拖拽"已经可用，**先让你能用起来** |
| **M2** | 图形界面 | `ui.py`：拖放区、预设与参数、结果区、后台线程、进度；文件对话框 |
| **M3** | 热键与单实例 | `hotkey.py`：`Ctrl+Alt+C` 全局热键、`summon`/`instant` 两种模式、单实例唤醒 |
| **M4** | 打磨 | 长截图切片完善、窗口内拖放（tkinterdnd2）、更友好的错误文案、README 使用说明 |

**P1（MVP 之后，按需追加）**：系统托盘图标 / 悬浮球、监视文件夹、`--install-hotkey` 自动生成快捷方式、把引擎换成 sharp 提速。

**P2（暂不考虑）**：浏览器插件或 DSH 客户端插件形式的"粘贴即自动压缩"、自动监视剪贴板。

> 关于 P2 的说明（为什么现在不做）：浏览器内自动压缩确实是步骤最少的方案（截图→Ctrl+V，就 2 步），但它需要伪造拖放事件把压缩后的文件塞进 DSH 的输入框，**依赖 DSH 前端内部实现**，DSH 一升级就可能失效；而且它只能覆盖"粘贴进页面"这一条路，对批量文件、长截图、命令行、以及"我要读本地图片"这些场景完全无能为力。所以它是"锦上添花"，不适合做地基。

## 16. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| tkinter 窗口内拖放需要额外小库 | M4 可能延期 | P0 先用"拖到 `imgc.cmd` 上"这种 Windows 原生机制顶上，功能不缺 |
| `ctypes` 写剪贴板（自建 DIB 结构）出错 | 粘贴出来是黑图/空 | M1 阶段先写独立的读写自测；失败时降级为"只保存文件 + 自动复制文件路径" |
| 全局热键被其他软件（截图工具、输入法）占用 | 召唤不了 | 热键可配置；注册失败给明确提示 + `.lnk` 备用方案 |
| DSH 未来版本改动限制数值 | 默认参数不再最优 | 参数全部可配；`imgc --check` 顺手能验证；文档 §2 记录了数值来源 |
| `ImageGrab.grabclipboard()` 遇到只放 PNG 格式、不放位图的来源 | 读不到图 | 用 `ctypes` 读注册格式 `PNG` 作为兜底（P1） |
| 单张 20MB 的大图处理耗时 | 界面等待感 | 后台线程 + 进度提示；必要时（P1）换 sharp 引擎 |

## 17. 术语小抄（给不熟悉这些词的人）

| 名词 | 通俗解释 |
|---|---|
| **长边** | 图片宽和高里数值更大的那个。限制是"单边 ≤2000px"，所以只要长边不超，就一定安全 |
| **base64** | 把图片这种二进制数据"翻译成纯文本字符"以便塞进网络请求，体积会膨胀约 1/3；这是 DSH 那条 20MiB 预算的由来 |
| **全局热键** | 不管当前开着什么程序，按下都能生效的按键组合（如 `Ctrl+Alt+C`）。靠 Windows 的 `RegisterHotKey` 实现 |
| **剪贴板格式（CF_DIB / PNG）** | 剪贴板是一张"多格式货架"，同一个内容可以同时以多种格式放上去，取用方挑自己认识的。浏览器偏爱 PNG 格式，画图/Word 偏爱位图格式 |
| **逼近目标体积** | 先按一个质量参数编码，超了就调低、没超就调高，反复几次直到刚好低于目标——像调水龙头 |
| **切片** | 把一张很高的长截图，按高度切成几张正常的图，每张之间重叠一点，避免把一行文字切成两半 |
| **互斥体（Mutex）** | Windows 提供的一种"命名锁"，用来判断"是否已经有一个我在运行"，避免开出一堆窗口 |
| **pythonw** | Python 的"无黑框"版本，用它启动图形界面不会弹出那个黑色命令行窗口 |
| **托盘图标 / 悬浮球** | 任务栏右下角小图标 / 桌面上那个能随手点的小圆球（都属于 P1） |
| **tkinter** | Python 自带的图形界面库，体积小、启动快，做这种小工具窗最合适 |
| **LANCZOS** | 一种高质量的图片缩放算法，缩小时比普通的"最近邻"清晰得多 |
